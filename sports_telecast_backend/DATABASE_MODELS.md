# Sports Telecast Backend - Database Schema Inventory

This document inventories all database tables and fields required by the FastAPI backend (as defined by SQLAlchemy ORM models and any direct SQL usages). It is intended to be used to validate that Alembic/SQL migrations in sports_telecast_db cover all necessary schema elements.

Generated by analysis of:
- src/database/models.py (SQLAlchemy ORM)
- src/database/repositories.py (direct SQL usages and assumptions)
- api/emoji_upload.py (legacy/minimal schema for emoji assets)
- src/database/schemas.py (conversion code that hints at fallbacks)

Note: All UUID fields use PostgreSQL UUID (as_uuid=True). Enums are PostgreSQL native enums created via Alembic (names indicated below).

## Enums

- sporttypeenum: ('football','basketball','tennis','cricket','rugby','hockey','baseball')

## Direct SQL usage notes

- src/database/repositories.py:
  - EmojiRepository.get_emojis includes a fallback text() query selecting emoji_id, emoji_type, file_location, created_at directly from emoji_assets. Schemas should ensure these columns exist or the fallback path remains viable. The backend is robust to missing image_url and name fields by deriving image_url from file_location and defaulting name from emoji_type.

- api/emoji_upload.py:
  - Defines a local declarative model (not used for migrations) for emoji_assets with: emoji_id (String(36)), emoji_type (String(32)), file_location (String(256)), created_at.
  - After upload, attempts best-effort: UPDATE emoji_assets SET image_url = :url WHERE emoji_id = :id (so migrations should add image_url Text nullable to emoji_assets).
  - This hints that legacy DB may only have file_location. Current ORM expects image_url, name, description, is_active, sort_order; backend handles absence gracefully in list endpoint but create_emoji_reaction validates emoji_type via ORM path (so emoji_type must be present).

## Summary of Critical Fields used by APIs

- Authentication/User endpoints (schemas.py convert_user_db_to_response):
  - Requires role, preferences (can be {}), created_at, updated_at; email, username, is_active, avatar_url, full_name
- Profiles endpoints:
  - Read/write many fields in user_profiles including JSON arrays and visibility enum; expects created_at/updated_at maintained
- Emoji endpoints:
  - List: reads emoji_id, emoji_type, image_url or derives from file_location
  - Capture reaction: validates emoji_type via emoji_assets.emoji_type; writes to user_emoji_reactions with user_id, event_id, emoji_id, created_at
  - Reaction summary: aggregates counts by emoji_id and joins with emoji_assets (requires emoji_type, image_url to present top_emojis)
- Highlights endpoints:
  - Need highlights table with fields listed above and FK to matches
- Matches and Events (repositories):
  - Query by enums, load relationships, order by start_date/start_time

## Compatibility and Migration Guidance

- Ensure all enums above are created as PostgreSQL types before tables reference them (Alembic scripts should use op.create_type or similar).
- emoji_assets.image_url should be nullable initially to avoid migration failures; backend derives image URL if missing.
- Consider maintaining legacy emoji_assets.file_location (Text or String) to support upload path and fallback behaviors.
- user_profiles.user_id must be UNIQUE to enforce one profile per user.
- schedule_matches must have a composite PK (schedule_id, match_id).
- All UUID PKs should be generated at DB or application; ORM defaults use uuid4().
